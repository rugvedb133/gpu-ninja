Before the capstone

Four assignments led up to this project — each one a small, contained lesson that fed into the final build.

  1. 01

    Matrix Addition

    The first kernel: element-wise addition on two 2D matrices. At a 256-thread block size, a 1000×1000 matrix needs roughly 63×63 blocks — and the last block along each edge isn't fully populated, so a bounds check keeps idle threads from writing past the array. Also the assignment that first put shared memory on my radar as an optimization lever.

  2. 02

    Reduction

    Summing a million-element array in parallel, the naive way and the warp-aware way. The naive kernel keeps every thread busy for exactly one of its nine steps before warp divergence sets in; restructuring which threads stay active cut simulated GPU cycles by about 30% and raised IPC by roughly 25%, measured in GPGPU-Sim.

  3. 03

    Tiled Matrix Multiplication

    Single-GPU tiled matmul — the direct ancestor of the capstone. Sweeping the tile size turned up a counter-intuitive result: 32×32 tiles cut global memory accesses the most, but ran slowest overall. 16×16 made more trips to memory and still won, because it balanced memory traffic against how much work — and how many threads — each block had to juggle.

  4. 04

    Histogram

    Building a 1024-bin histogram without every thread colliding on the same global counters — each block gets a private copy of the histogram, accumulates locally with atomics, then merges into the shared result at the end.

Assignment 1 flagged shared memory as the obvious next optimization. The capstone went a different way — Unified Memory instead — for reasons that show up later in this page.

The problem

Matrix multiplication is embarrassingly parallel — every output element is an independent dot product — which makes it a natural GPU workload. The real question this project set out to answer was less "can a GPU do this faster than a CPU" (yes, decisively) and more: does splitting the work across multiple GPUs actually beat running it on just one?

One housekeeping detail baked into the algorithm from the start: matrix multiplication doesn't commute, so A×B and B×A aren't the same computation — which matters the moment you start deciding which piece goes to which device.

Meet Bender

Everything ran on UCR's shared GPU cluster node — "Bender" to anyone who's SSH'd in, complete with its own ASCII-art welcome banner. Four RTX 2070s meant four independent multiplication targets to split the work across; the dual Xeons and 256GB of host RAM meant the CPU side was never going to be the bottleneck.
