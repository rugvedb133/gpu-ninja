Matrix multiplication, spread across four GPUs

A capstone project for GPU Architecture and Parallel Programming: splitting one matrix multiplication into four independent pieces and handing each to its own NVIDIA GPU.

Before the capstone

Four assignments led up to this project, each one a small, contained lesson that fed into the final build.

  1. 01

    Matrix Addition

    The first kernel: element-wise addition on two 2D matrices. At a 256-thread block size, a 1000×1000 matrix needs roughly 63×63 blocks, and the last block along each edge isn't fully populated, so a bounds check keeps idle threads from writing past the array. Also the assignment that first put shared memory on my radar as an optimization lever.

  2. 02

    Reduction

    Summing a million-element array in parallel, the naive way and the warp-aware way. The naive kernel keeps every thread busy for exactly one of its nine steps before warp divergence sets in; restructuring which threads stay active cut simulated GPU cycles by about 30% and raised IPC by roughly 25%, measured in GPGPU-Sim.

  3. 03

    Tiled Matrix Multiplication

    Single-GPU tiled matmul: the direct ancestor of the capstone. Sweeping the tile size turned up a counter-intuitive result: 32×32 tiles cut global memory accesses the most, but ran slowest overall. 16×16 made more trips to memory and still won, because it balanced memory traffic against how much work and how many threads each block had to juggle.

  4. 04

    Histogram

    Building a 1024-bin histogram without every thread colliding on the same global counters: each block gets a private copy of the histogram, accumulates locally with atomics, then merges into the shared result at the end.

Assignment 1 flagged shared memory as the obvious next optimization. The capstone went a different way instead, using Unified Memory, for reasons that are explained later in this page.

The problem

Matrix multiplication is embarrassingly parallel: every output element is an independent dot product, which makes it a natural GPU workload. The real question this project set out to answer was less "can a GPU do this faster than a CPU" (yes, decisively) and more: does splitting the work across multiple GPUs actually beat running it on just one?

One important detail

Matrix multiplication doesn't commute, so A×B and B×A aren't the same computation, which matters the moment you start deciding which piece goes to which device.

Meet Bender

Everything ran on UCR ECE dept's shared GPU cluster node, "Bender". Four RTX 2070s meant four independent multiplication targets to split the work across; the dual Xeons and 256GB of host RAM meant the CPU side was never going to be the bottleneck.

The approach

Once the plan was to use all four GPUs, the mechanics came down to three things: how the work gets split, how four devices stay busy without blocking each other, and how memory moves between them.

Splitting the multiplication

Matrix A gets sliced into two row-blocks (A1, A2); matrix B into two column-blocks (B1, B2). That turns one N×N multiplication into four independent, smaller ones (A1×B1, A1×B2, A2×B1, and A2×B2) each producing one quadrant of the result matrix C. Four independent sub-problems, four GPUs: cudaSetDevice() sends each one to a different device before its kernel launches.

Keeping four GPUs busy at once

Dispatching four kernels to four devices only helps if they can actually run concurrently instead of queuing up behind each other. CUDA streams handle that by giving each GPU its own stream, so the host can launch all four kernels back-to-back without waiting for one to finish before starting the next.

Unified Memory

The foundations track flagged shared memory as the obvious next optimization after Assignment 1. This project reached for a different tool instead: Unified Memory (cudaMallocManaged), which lets the CPU and every GPU address the same memory without an explicit host-to-device copy for each buffer. It trades away some of the fine-grained control shared memory would give you for a lot less bookkeeping across four devices at once; a reasonable trade when the thing you're debugging is "did I even target the right GPU", not "is this kernel memory-bound."

Loops vs. writing it out

The four device-dispatch blocks are nearly identical, with different device ID, different source and destination pointers, but same overall shape. The obvious move is a loop. In practice however, the four blocks didn't stay identical enough: stream assignment, host-side offsets, and which quadrant fed which output diverged just enough that a loop would have needed its own set of conditionals to handle each case anyway.

In the end, it was easier to write each calculation directly without using a loop. While this increases the size of the code, it reduces the programming complexity.

Results

Comparison of execution times, benchmarked at the default 1000×1000 size: five phases, single GPU against all four.

The real win is in executing the kernel: 0.004720s down to 0.000048s, roughly a 98× drop, since each GPU now computes a quarter of the work at the same time instead of one GPU computing all of it in sequence. The real cost shows up first: setting up the problem got noticeably slower under multi-GPU, coordinating four streams and switching device contexts isn't free. Even counting that overhead in, the original conclusion still stands: multi-GPU comes out ahead overall.

Limitations

Not everything made it into the final version, some by choice, some by deadline.

  • Square matrices only. The program only handles square matrices: Amm×Bmm=Cmm. Supporting non-square shapes means more careful block-splitting logic and, realistically, more GPUs to keep the split balanced.
  • Fixed 50/50 split. Rows and columns are always divided exactly in half. There's no logic yet to rebalance for odd dimensions, or to scale past this 2×2 grid of GPUs.
  • Non-square support was attempted, not finished. Between the time left in the project and Bender being a shared server with its own limits, I wasn't able to validate it properly before the deadline.

Streams across four devices also took real trial and error. Launching a kernel on a stream is one thing; keeping four separate device contexts and their streams straight at once, without them stepping on each other, took longer to get right than originally thought.

Reflection

Looking back, the matrix multiplication itself was the easy part. The real lesson was that scaling across devices is mostly a coordination problem, not a compute problem.

The results section makes that concrete: the kernel got 98× faster, but just standing up four streams and switching device contexts costs more time than a single GPU ever needed to spend getting started. That overhead is the real price of parallelism across separate devices, and it's easy to miss if only looking at compute time.

The loop-vs-explicit-code decision taught a smaller, related lesson: four almost-identical blocks of code aren't actually identical once you look closely, and forcing them into a shared abstraction cost more in conditionals than it saved in line count. Sometimes the less clever version is the right one.

If I picked this back up, non-square matrices are still the obvious next step. Past that, I'd want to test whether the split has to be a fixed 50/50: with matrices that don't divide evenly, or with more than four devices, a fixed 2×2 grid stops being the right shape.
